Case study · Client work

Proprietary Operations & Data Platform

Production · private Ask about this work

An internal multi-role application behind a large, multi-stakeholder operational program.

The platform handles approvals, task routing, support, and reporting, and keeps several existing business systems in step through Python services and APIs. It began as disconnected scripts and manual handoffs. Today it's an integrated production application. A newer database-backed generation, built on PostgreSQL and moving toward managed integrations and centralized data access, has been built and demonstrated; production still runs on the original platform.

My role
Technical lead
Timeline
April 2025 – present
Status
Production · private
Stack
Production: Python, FastAPI, SQLAlchemy, SQLite, REST APIs. Next generation: PostgreSQL.

The problem

The program's work was spread across several business systems, joined by manual handoffs and standalone scripts. The rules changed mid-cycle, the workload was large, and the people doing the work couldn't stop while the software caught up.

What I owned

  • Turning shifting stakeholder requirements into workflows and detailed task instructions for coding agents.
  • Designing the data flows, integrations, and the schema for the database-backed version.
  • Directing Claude and other coding agents, then reviewing what they produced.
  • Validating UI behavior and edge cases in the browser, and troubleshooting frontend and backend interactions.
  • Deciding when a change was ready to reach the people who depend on it.

The hard parts

Engineering decisions

Mid-cycle reconciliation workflow

Built during a live cycle: distinct data sources reconciled into team working files, with updates flowing both ways.

The decision

Two-way sync means two writers. The workflow had to keep team files and the central record consistent while people kept working in them.

Unattended synchronization

Scheduled synchronization across many working files, with no one watching.

The decision

Treat rate limits and partial API failures as normal. The sync backs off and retries, reports structured health information, and preserves what people entered by hand. Bulk changes run as a dry run first, and repairs back up each file before touching it.

Permission-aware interfaces

Role-specific views in one application, replacing direct work in shared spreadsheets.

The decision

Each role sees and changes only what it should, while the systems underneath stay in sync.

Human-in-the-loop AI support workflow

A workflow designed so that a model classifies and researches incoming support requests and prepares a proposed action.

The boundary

The model proposes. A person approves before anything consequential changes.

Status

Designed and in development. I'm not presenting it as a production feature.

Production data-integrity repair

Diagnosed a live data-integrity problem and reconstructed the affected records from the source system's revision history.

The decision

Fixing the records wasn't enough. I traced the problem to a defect in the upstream template and fixed it there, so the same failure is less likely to come back.

Database-backed next generation

PostgreSQL with relational models, versioned migrations, and automated tests, moving toward managed integrations and centralized data-access boundaries.

Status

Built and demonstrated to stakeholders. Production still runs on the original platform.

Validation

I personally validate UI behavior and edge cases in the browser, and troubleshoot the interactions between frontend and backend when something's off. The data-integrity repair is the clearest example of the principle: restore the records, then find and fix what caused them to break.

Outcome

A working production capability the program relies on, and specific problems solved along the way: a reconciliation workflow delivered in the middle of a live cycle, synchronization that recovers from routine API failures without losing human edits, and a data defect fixed at its source. Demonstrations of the newer generation helped establish confidence in the platform and opened discussions about expanding its responsibilities.

Case study · AI evaluation

AI-Assisted Learning Platform

Prototype · private Ask about this work

An AI tutor that guides instead of answering, and model-drafted assessments that stay advisory until a teacher reviews them.

The platform looks at how a student works with an AI tutor, not only at what they turn in: whether they set a goal, ask clearly, check what comes back, and stay honest about which work is theirs. The prototype has separate views for students, teachers, parents, and administrators.

Status
Prototype · private
Focus
Prompt evaluation and human review
Built with
Python, FastAPI, React, TypeScript, PostgreSQL, OpenAI models

The problem

A finished assignment says little about how a student used AI to produce it. The goal was to assess the process, using the tutoring conversation as evidence, without letting a model make grading decisions on its own.

What I built

Scope

A tutor that guides

The tutor is designed to ask guiding questions rather than write the work for the student.

Structured evaluation criteria

Each criterion is defined by observable behaviors a teacher can point to in the conversation, not by a general impression.

Model-drafted, teacher-reviewed

The model drafts an assessment and flags supporting evidence from the conversation.

The boundary

The model's draft is labeled as the AI's. A teacher records their own judgment for each criterion beside it, and only then is the work marked teacher-reviewed.

Role-specific views and curriculum tools

Separate experiences for each role, plus tools that turn uploaded course documents into lessons.

Evaluating and correcting the model

An early QA pass found that the model's evidence suggestions were often false positives: it matched a student's general impression instead of observable behavior. I rewrote the prompt to ground each suggestion in an explicit checklist of observable behaviors for that criterion and to name the specific behavior it matched. A small read-only retest on the same submissions showed fewer false positives without losing the genuine match, and the teacher's review stays the final word.

Invented example / no model call

What counts as evidence?

This illustrates the distinction behind the prompt correction. It is not a real student's work or a recorded evaluation result.

A vague claim

“I checked the answer. It looks right.”

This does not name an observable checking action. A model should not infer one from confidence.

An observable action

“I compared the date with the museum catalogue and corrected the year in my draft.”

The statement names what was checked, how, and what changed. A teacher still makes the judgment.

Inspect the illustrative instruction
Suggest evidence only when a quoted conversation turn names an observable action for the criterion. Cite the turn and the action. If the behavior is absent or ambiguous, return insufficient evidence. Do not infer verification from a general claim of confidence.

    Modeling
    Data relationships across systems
    
        
    
          
    Much of my work is deciding how things relate when they live in different systems. The same person, assignment, or item can appear in several places under different identifiers. I map those entities and their relationships, decide which system owns each piece of data, build crosswalks between identifiers, and model who can see or change what. Then I expose all of it through application workflows instead of shared spreadsheets.
