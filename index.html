Case study · Client work

Proprietary Operations & Data Platform

Production · private Ask about this work

An internal multi-role application behind a large, multi-stakeholder operational program.

After months spent connecting and automating existing workflows, I saw that the operation needed a real application to keep growing. I proposed and initiated the platform, then led the work of connecting the systems and refining it with the people who use it. Today it handles approvals, task routing, support, and reporting, and keeps several existing business systems in step through Python services and APIs. A newer database-backed generation, built on PostgreSQL, has been built and demonstrated; production still runs on the original platform.

My role
Initiated it · technical lead
Timeline
April 2025 – present
Status
Production · private
Stack
Production: Python, FastAPI, SQLAlchemy, SQLite, REST APIs. Next generation: PostgreSQL.

The problem

The program's work was spread across several business systems, joined by manual handoffs and standalone scripts. The rules changed mid-cycle, the workload was large, and the people doing the work couldn't stop while the software caught up.

What I owned

  • Proposing the application in the first place, after building the workflow automations it replaced.
  • Turning shifting stakeholder requirements into workflows and detailed task instructions for coding agents.
  • Designing the data flows, integrations, and the schema for the database-backed version.
  • Directing Claude and other coding agents, then reviewing what they produced.
  • Validating UI behavior and edge cases in the browser, and troubleshooting frontend and backend interactions.
  • Deciding when a change was ready to reach the people who depend on it.

The hard parts

Engineering decisions

Mid-cycle reconciliation workflow

Built during a live cycle: distinct data sources reconciled into team working files, with updates flowing both ways.

The decision

Two-way sync means two writers. The workflow had to keep team files and the central record consistent while people kept working in them.

Unattended synchronization

Scheduled synchronization across many working files, with no one watching.

The decision

Treat rate limits and partial API failures as normal. The sync backs off and retries, reports structured health information, and preserves what people entered by hand. Bulk changes run as a dry run first, and repairs back up each file before touching it.

Permission-aware interfaces

Role-specific views in one application, replacing direct work in shared spreadsheets.

The decision

Each role sees and changes only what it should, while the systems underneath stay in sync.

Human-in-the-loop AI support workflow

A workflow designed so that a model classifies and researches incoming support requests and prepares a proposed action.

The boundary

The model proposes. A person approves before anything consequential changes.

Status

Designed and in development. I'm not presenting it as a production feature.

Production data-integrity repair

Diagnosed a live data-integrity problem and reconstructed the affected records from the source system's revision history.

The decision

Fixing the records wasn't enough. I traced the problem to a defect in the upstream template and fixed it there, so the same failure is less likely to come back.

Database-backed next generation

PostgreSQL with relational models, versioned migrations, and automated tests, moving toward managed integrations and centralized data-access boundaries.

Status

Built and demonstrated to stakeholders. Production still runs on the original platform.

Validation

I personally validate UI behavior and edge cases in the browser, and troubleshoot the interactions between frontend and backend when something's off. The data-integrity repair is the clearest example of the principle: restore the records, then find and fix what caused them to break.

Outcome

A working production capability the program relies on, and specific problems solved along the way: a reconciliation workflow delivered in the middle of a live cycle, synchronization that recovers from routine API failures without losing human edits, and a data defect fixed at its source. Demonstrations of the newer generation helped establish confidence in the platform and opened discussions about expanding its responsibilities.

Case study · AI evaluation

AI-Assisted Learning Platform

Prototype · private Ask about this work

An educational AI prototype built around a simple principle: AI should help students learn, not do their thinking for them.

It also explores how AI can help teachers evaluate the learning process while keeping people responsible for final decisions. The platform looks at how a student works with an AI tutor, not only at what they turn in: whether they set a goal, ask clearly, check what comes back, and stay honest about which work is theirs. The prototype has separate views for students, teachers, parents, and administrators.

Status
Prototype · private
Focus
Prompt evaluation and human review
Built with
Python, FastAPI, React, TypeScript, PostgreSQL, OpenAI models

The problem

A finished assignment says little about how a student used AI to produce it. The goal was to assess the process, using the tutoring conversation as evidence, without letting a model make grading decisions on its own.

What I built

Scope

A tutor that guides

The tutor is designed to ask guiding questions rather than write the work for the student.

Structured evaluation criteria

Each criterion is defined by observable behaviors a teacher can point to in the conversation, not by a general impression.

Model-drafted, teacher-reviewed

The model drafts an assessment and flags supporting evidence from the conversation.

The boundary

The model's draft is labeled as the AI's. A teacher records their own judgment for each criterion beside it, and only then is the work marked teacher-reviewed.

Role-specific views and curriculum tools

Separate experiences for each role, plus tools that turn uploaded course documents into lessons.

Evaluating and correcting the model

An early QA pass found that the model's evidence suggestions were often false positives: it matched a student's general impression instead of observable behavior. I rewrote the prompt to ground each suggestion in an explicit checklist of observable behaviors for that criterion and to name the specific behavior it matched. A small read-only retest on the same submissions showed fewer false positives without losing the genuine match, and the teacher's review stays the final word.

Invented example / no model call

What counts as evidence?

This illustrates the distinction behind the prompt correction. It is not a real student's work or a recorded evaluation result.

A vague claim

“I checked the answer. It looks right.”

This does not name an observable checking action. A model should not infer one from confidence.

An observable action

“I compared the date with the museum catalogue and corrected the year in my draft.”

The statement names what was checked, how, and what changed. A teacher still makes the judgment.

Inspect the illustrative instruction
Suggest evidence only when a quoted conversation turn names an observable action for the criterion. Cite the turn and the action. If the behavior is absent or ambiguous, return insufficient evidence. Do not infer verification from a general claim of confidence.

Systems Map

Not every problem needs AI. Every problem needs the right solution.

A lot of my work happens between systems that weren't designed to work together. Spreadsheets, databases, APIs, documents, and people all need to exchange information, and somewhere in the middle, something has to make sense of it. That's where I do some of my favorite work.

I use Python to connect the pieces, organize the rules, automate the repetitive work, and build applications around the people who use them. AI coding agents help me build those solutions faster than I could have imagined a few years ago. But whether the finished application needs AI running inside it is an entirely different question.

Business problems

An API rate-limits requests

Standard Python

The problem
An integration starts getting HTTP 429 (“too many requests”) responses from a business API.
How I'd approach it
Stay inside the rate limit, retry with bounded exponential backoff, and log a structured outcome so an unattended job never fails silently.
Where AI fits
Nowhere at runtime. The rules are known in advance, and calling a model on every failure would add cost and guesswork without making anything more reliable.
  1. Response detected
  2. Back off and retry
  3. Record the outcome, or escalate when retries run out

In productionThe production platform's sync handles rate limits this way. The picture is simplified, and retries reduce failures; they can't promise every request succeeds.

Records disagree across systems

Standard Python

The problem
The same person or item appears in several systems under different IDs, and their updates don't agree.
How I'd approach it
Map identifiers between systems, decide which system owns each field, validate, and reconcile by explicit rules. Anything the rules can't settle gets flagged for a person instead of guessed.
Where AI fits
Not at runtime. When the rules are knowable, deterministic code is cheaper, testable, and explainable.
  1. Match identifiers
  2. Check the owning system for each field
  3. Reconcile, or flag the conflict

IllustrativeDrawn from real integration and data-modeling work. It isn't a claim that one generic implementation covers every system.

A support request arrives as free text

AI may help · a person reviews

The problem
A support message arrives in someone's own words, and staff have to work out what it's asking before anyone can act.
How I'd approach it
A narrowly scoped model can earn its place here: classify the request, research it against sources it's allowed to use, and propose an action. A person approves before anything consequential changes.
Where AI fits
One narrow job: reading unstructured text and suggesting a next step. The model never makes the change itself.
  1. Request arrives
  2. Scoped AI suggestion
  3. A person approves
  4. Authorized workflow runs

In developmentDesigned and in development for the operations platform. It isn't a production AI feature.

Assessing evidence of learning

AI may help · a teacher reviews

The problem
Student work has to be judged against defined criteria, not a model's general impression.
How I'd approach it
Ground the prompt in observable behaviors for each criterion, have the model cite the evidence it found, and keep the teacher's judgment separate and final. No unreviewed AI grading.
Where AI fits
A drafting assistant whose suggestions are labeled as the AI's. The teacher records their own judgment beside them.
  1. Criteria and student work
  2. Model drafts evidence
  3. Teacher records their judgment

Prototype · privateFrom my private learning-platform prototype. Students can see the AI's labeled feedback before a teacher reviews it; the teacher's judgment is the final word.

Reports from structured records

Standard Python

The problem
Consistent documents have to be produced from validated records, again and again.
How I'd approach it
Validate against a schema, map fields deterministically, fill templates, and make the output reproducible.
Where AI fits
Not at runtime. AI coding tools can help write a system like this, but no model needs to run for each report. The same inputs should always give the same document.
  1. Validate the records
  2. Apply the business rules
  3. Produce the document

Two different questions

Building with AI isn't the same as running AI

How I use AI to build

Claude and Codex help me write and refine the code for nearly everything I build, this page included. I decide what gets built, review what they produce, and test it myself.

Does the finished system use AI?

Only where it earns its place. Most of the problems on this map are solved with ordinary Python and no model calls. In a business workflow, a model that runs inside the application gets one narrow job, and a person reviews what it suggests. My games are a different story: there, the AI is the fun part.

Nothing on this page calls a model or a live system. Choosing a problem just switches what's highlighted.

The principle

I'm not looking for places to squeeze AI into every workflow. I'm looking for the best way to solve the problem.

Sometimes that's a carefully scoped AI agent with a person making the final decision. Sometimes it's 200 lines of well-designed Python. And sometimes the smartest solution is simply fixing the process before writing anything at all.

What I hope this shows: systems integration, architectural judgment, practical AI evaluation, reliable automation, and knowing the difference between building software with AI and building software that uses AI.

How I work

From a messy workflow to a working application.

Coding agents write a lot of my code, and I'm accountable for all of it. Here's the loop I follow.

  1. 01

    Understand the problem

    What is actually happening, where do people get stuck, and what must the solution do?

  2. 02

    Define success

    Agree on inputs, ownership, constraints, edge cases, and how the behavior will be tested.

  3. 03

    Direct the agents

    Give Claude or Codex a scoped task, review the work, and iterate with precise feedback.

  4. 04

    Try it as a user

    Click through each role, form states, unusual inputs, duplicate submissions, and failure paths in a real browser.

  5. 05

    Find the actual cause

    Trace bugs across frontend, services, and data instead of patching symptoms, then retest.

  6. 06

    Release carefully

    Validate changes, add diagnostics and recovery paths like retries, dry runs, and backups, and make sure consequential actions have the right boundaries.

Modeling

Data relationships across systems

Much of my work is deciding how things relate when they live in different systems. The same person, assignment, or item can appear in several places under different identifiers. I map those entities and their relationships, decide which system owns each piece of data, build crosswalks between identifiers, and model who can see or change what. Then I expose all of it through application workflows instead of shared spreadsheets.

The useful questions are concrete: which record is this, which system owns it, and who is allowed to change it?
